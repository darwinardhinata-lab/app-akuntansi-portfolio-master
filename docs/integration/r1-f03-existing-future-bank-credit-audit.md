# F03 — read-only inventory of already-posted future bank credits

Do not run on staging, the primary database, or production as part of this change. Use an explicitly authorized read-only snapshot or disposable restored copy. Do not change journal dates, reverse entries or release holds automatically. This is a detection procedure, not a migration.

1. Record the snapshot time and the Asia/Jakarta business day (`ErpBankBalance::businessDate()`). Resolve `ppl.bank.<id>` from the configured payment accounts and active `company_coa_mappings`, per company. Record the mapping used; current mapping cannot reconstruct older mapping history.
2. For each resolved GL account, start with the same journal scope as `ErpBankBalance::ledgerLines()` (`ProtectedJournalQuery`). Join `journal_details` to `journal_headers` by `journal_id`. Report positive `KREDIT` and negative `DEBET` with `DATE(transaction_date) > :jakarta_business_day`, using bound date and account parameters. Retain journal ID, date, source reference/type, line ID and actual stored amount. If looking for credits that were future *when posted* but have already become effective, compare the GL date to the Jakarta calendar date of a trustworthy posting timestamp instead. `created_at` alone is not sufficient for an edited, replaced, or historically imported journal.
3. Include **all** signed bank lines (not just flagged lines) when evaluating each effective date's net movement. Use stored GL amounts, treating `DEBET` as positive and `KREDIT` as negative, and distinguish a scenario based on current holds from an actual historic balance. Reconcile actual, active holds and unposted payment events separately; do not add an event already represented in GL a second time.
4. Send journal/source references, effective date, balance exposure and uncertainty to Accounting. Obtain a separate decision for each correction, preserving linked source and audit history.
